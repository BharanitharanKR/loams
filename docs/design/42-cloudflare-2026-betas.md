Status: **Proposed** · 2026-10-02. The owner's direction of 2026-10-02: "search the latest beta features in the Cloudflare blog and use them." Hosted-service choices (Containers, Dynamic Workers, the Monetization Gateway, the Data Platform as a hosted analytics backend) are in the private `loams-platform` repository, docs 03 to 07, and follow [open-core.md](../open-core.md). ## 1. Summary

Four Cloudflare integrations (three betas or drafts, and one GA product) become open adapters, each behind a trait Loams already has or is about to have, so none of them is a dependency of self-hosting (D560):

| Beta | Open adapter | Default |
|---|---|---|
| Artifacts | `ArtifactsRemote` for Loams Git (§36): a mirror sink and a workspace host, **not** a `WalStore` or `RefLog` | The bucket WAL stays the default (D561, D562) |
| Browser Run, with Kitesurf as an option | A `remote` provider in the web-bridge toolbox (§37 §18.14), which **answers Q507** | Client-tool relay for credentialed sessions, `remote` for unattended public-web work (D565, D566) |
| WebMCP | Console and plugin actions registered as WebMCP tools; the bridge calls a page's tools | Progressive enhancement behind feature detection (D568, D569) |
| Basin Catalog (formerly R2 Data Catalog, GA 2026-10-01) | An external Iceberg REST catalog in `loams-iceberg` | Lakekeeper stays the default; read first (D571, D572) |

Two more betas are only cross-referenced here: Containers filesystem snapshots for factory runs (§39 SF4, D574) and Emscripten Rust for Workers (private, CF1, D576).

## 3. Artifacts as a Loams Git provider (D561–D564)

Artifacts is "a versioned file system that speaks Git": repositories, forks, files, commits and repo-scoped Git tokens, through a Workers binding. That is a **Git-level** service, while §36's traits sit **below Git**:

| §36 trait | What it needs | Artifacts |
|---|---|---|
| `WalStore` | Fenced, monotonic, contiguous append of segments | Not offered; a repository is not an append log |
| `RefLog` | Atomic multi-ref transactions, linearizable, idempotent on a key | Not documented **(unverified)**; Git ref updates are per ref |
| `BlobStore` | Create-only content-named blobs, range reads | Git objects only, 32 MB per blob, 1 GB per repository: the limits alone rule it out for packs and the build cache (§36 §8) |
| `Materializer` | Scoped, on-demand blob fetch for agents | A fit: files and commits are readable through the binding |

**D561: the bucket WAL stays the default and the source of truth.** Artifacts cannot be a `WalStore` or `RefLog` provider. **D562: the open adapter is `ArtifactsRemote`, a crate `loams-git-artifacts` (Apache-2.0)** with two roles: (a) a **mirror sink**: after a Loams commit, push the same commit to an Artifacts repository so Cloudflare Workers Builds and any Git client on that platform see it (the WAL remains the writer; the mirror is rebuildable); (b) a **`Materializer` and workspace host** for agent workspaces (§15): fork a repository, hand an agent a repo-scoped token that §36 §6's scope model mints, and import the result back as a proposed patch. **D563: tokens** minted by Artifacts are never stored in the WAL; they are held by the credential broker like any other (§39 §6). **D564: the hosted use** (Loams Cloud repositories on Cloudflare, quotas, per-tenant namespaces and jurisdiction) is private, in loams-platform doc 04. The adapter needs a Workers binding or Cloudflare's REST API; it is compiled out of self-host builds unless enabled.

## 4. A remote provider for the web toolbox (D565–D567), and the answer to Q507

§37 §18.14.6 left **Q507** open: how do server-side agents (the Factory's, SF2) get web tools when their app lacks an API feature? The recommended default (**D565**):

1. **Credentialed work uses the client-tool relay** (the person's own desktop runs the bridge tool; credentials never leave their machine).
2. **Unattended, public-web or app-with-service-account work uses a `remote` provider**: same tool contract as the local Tauri bridge (§18.14.2: snapshot with uids, `find`, `click`, `fill`, `wait_for`, no cookie or storage tools), implemented over a remote browser's CDP endpoint.

**D566: the adapter targets Browser Run's CDP and Playwright endpoints**, which are documented and stable, not Kitesurf's own API. Kitesurf is selectable *inside* Browser Run, so it works when the account has it, but it is closed source with an unspecified future licence, so nothing may depend on it (a Playwright MCP container remains the self-host provider, Apache-2.0, as §18.14.6 D512 already says). **D567: a remote browser is a third party**, so the provider refuses `secret_ref` fills of user credentials by default. Service-account `secret_ref` fills require a configured hostname allowlist, and the provider rejects `fill` on a non-allowlisted page; D507 redaction applies to these fills and to snapshots, logs, traces and console output. It keeps no persistent profile unless the organisation enables one, and records every call in the same audit and trace path (§39 §9). The provider is a trait implementation in `loams-web-bridge`'s core; running it as a hosted service is private (loams-platform doc 04).

**What AP1c added, from the documentation read on 2026-10-03** ([docs/remote-browser-provider.md](../remote-browser-provider.md)).
- **The endpoint**: `wss://api.cloudflare.com/client/v4/accounts/{account_id}/browser-run/devtools/browser` acquires a session and speaks CDP on the same socket, authenticated with `Authorization: Bearer <API_TOKEN>` (the token needs **Browser Rendering — Edit**). Some pages and the Puppeteer examples use the `browser-rendering` path, the same endpoint under its former product name.
- **Guardrails, which is the answer to egress.** An optional `cf-brapi-guardrails` header carries base64url JSON of `allowedDomains` (50 at most) and `allowedDomainSets` (four at most), and Browser Run blocks every request the session makes outside them: the sub-resources and redirects a caller never sees. **It is not supported on Kitesurf**, which is why the adapter refuses an allow-listed Kitesurf session by default instead of running with the enforcement layer missing.
- **The engine default, written down.** `engine` is `chromium` unless an operator writes otherwise. Kitesurf is offered for the stateless work — a one-shot scrape, a content extraction, an approximate screenshot of a **public** page — and refused for anything credentialed or long-lived, on Cloudflare's own statement that it cannot keep a durable authenticated session. Recommending Kitesurf for a logged-in flow would be actively wrong: the credentials would be typed into a browser that cannot keep the session state and cannot clear a bot challenge.
- **Cost controls**, because the adapter is optional but the invoice is not: a concurrency ceiling, a minimum gap between new sessions and a per-UTC-day local budget, all defaulting to the free plan's numbers. These are a guard against a runaway loop, not a meter; §10 §6 keeps metering private.
- **The `keep_alive` bound is ambiguous in Cloudflare's own pages** (Q567): the CDP table allows up to 1 200 000 ms, the FAQ and the limits page say ten minutes. The adapter sends at most ten minutes, which both readings accept.
- **Live verification is outstanding**: no Cloudflare credentials were available, so the adapter is implemented against the documented interface and its tests run against a scripted CDP connection. The unverified points are listed in the provider document §6.

## 5. WebMCP in the console and plugins (D568–D570, D635, D638)

WebMCP lets a page register tools with `document.modelContext.registerTool`, so an agent calls a function instead of driving the UI. Its status is a **Community Group draft**, so it is an enhancement, never the only path (**D568**).

- **D569, the cordis console and plugins.** The console registers one WebMCP tool per **plugin action** that is already an MCP tool or a Connect method, through a small `webmcp` module of the console: feature-detected (`document.modelContext` present), registered with `exposedTo` set to the console's own origin plus the paired agent origins, and unregistered on sign-out (the `signal` option). The tools are generated from the same action registry as the stdio MCP server (§30), so there is one description of each action. Each tool enforces the user's OpenFGA permissions and the approvals of §39 §8 exactly as the UI would.
- **D570, the bridge.** §18.14.2 lists WebMCP as "left out of v1". It joins v2 as two tools: `list_webmcp_tools` and `call_webmcp_tool`, which prefer a page's registered tools over snapshot-driven clicks when present. This also gives agents a lighter path into the framed apps of §39 once those apps expose WebMCP (none is known to; **unverified**).

**What AP1d Task 0 established, from the sources read on 2026-10-05** (answers Q568). Every claim below is from a primary source: the spec's own text, or the vendor's own tracker. Secondary reporting was not used and, where it disagreed, is corrected below.
- **The entry point is `document.modelContext`, confirmed from the IDL**, not inferred from prose. It is a `partial interface Document` addition, `[SecureContext, SameObject]`, so it is absent in a non-secure context and the same object for a document's lifetime. `ModelContext` is `[Exposed=Window, SecureContext]` and extends `EventTarget`. The older `navigator.modelContext` spelling appears in third-party guides and in older drafts; the spec does not define it.
- **The whole surface, so Task 1 can be written against something real:** `registerTool(tool, options)` → `Promise<undefined>`, `getTools(options)` → `Promise<sequence<RegisteredTool>>`, `executeTool(tool, inputObject, options)` → `Promise<DOMString>`, plus `ontoolchange`, `ontoolactivated` and `ontoolcancel`. `ModelContextTool` requires `name`, `description` and `execute`, and optionally takes `title`, `inputSchema` and `annotations` (`readOnlyHint`, `untrustedContentHint`, `consequentialHint`, `debugging`, all defaulting to false). The `execute` callback receives `(inputObject, { signal })` — that signal is the execution-time lifetime, distinct from the registration-time `signal` that unregisters.
- **Registration-time `signal` unregisters; it does not cancel a running call.** The spec says so explicitly, and it is the reason sign-out needs an abort per registered tool rather than one global flag.
- **`exposedTo` is a list of origin strings that must each be potentially trustworthy**, or the whole `registerTool` promise rejects with a `SecurityError`. This is stricter than it looks: a plaintext `http://` agent origin cannot be listed at all. Worth knowing before D569 pairs a console with an agent origin.
- **A bare registration with no `exposedTo` is same-origin only** — `exposed origins` starts as an empty list and *tool is exposed to an origin* returns true on same-origin regardless. So the secure default is correct without any option, which is what we want.
- **Access is gated by a `tools` Permissions Policy** with default allowlist `['self']`. A console that wants an agent origin to reach its tools must opt that origin in via the header; the API rejects with `NotAllowedError` otherwise.
- **Chrome is trialling, not shipping.** Chrome Status 5117755740913664 reads: dev trial 146, origin trial **149 to 156**, and **no shipping milestone**. As of this reading Chrome 155 is stable and 156 is in beta, so the trial ends at 156 and no ship decision exists yet. A third-party aggregator claimed the feature is pencilled for 157; that is not on the primary page and is not relied on here.
- **Edge runs its own origin trial, and it runs much longer than reported.** Microsoft's own trial page states an expiration of **2027-03-30**. A widely-cited secondary source said 17 November 2026; the primary source says otherwise, and the primary source wins.
- **Firefox is neutral and actively implementing, behind a pref.** Mozilla standards-positions #1412 is closed with `position: neutral`. Bugzilla 2018306 ("Implement a prototype WebMCP API") is assigned and **NEW**, carries the `behind-pref` flag and tracking for firefox157–159, and two of its children are already **RESOLVED FIXED**: the content-process imperative implementation (2018320) and the main-process service for tool enumeration and invocation (2018323). So the earlier reading of "no commitment from Firefox" was wrong in the direction that matters: there is no commitment to ship, but there is real and advanced work in progress.
- **Safari is the outlier, and it is the risk.** WebKit standards-positions #670 is **closed** and labelled **`position: oppose`**, with concerns across API design, duplication, privacy, security, venue and meaningful user consent. Not "no commitment" — a formal objection. The design's "experimental, never the only path" posture (D568) is therefore load-bearing rather than merely prudent, and no part of AP1d may assume WebMCP is ever available.
- **`requestUserInteraction()` does not exist in this draft.** Chrome's security documentation mentions it while discussing consent management; the current spec text has no such method. Anything written against it would be writing against a proposal.

**Still unverified after Task 0:** the wpt.fyi pass counts per engine (the results page renders client-side and could not be read), and the Chrome origin trial's exact end-of-trial behaviour once 156 ships. Neither blocks Task 1, which is feature detection.

**What AP1d Task 2 built (D636): the action registry the tools are generated from.** Task 1 had a registration seam and no notion of a tool's meaning; there was no plugin action registry anywhere in the repository, so Task 2 wrote one.

- **The registry** is `ActionRegistry` in `@loams/console-host` (`web/packages/console-host/src/actions.ts`), provided by the host as the **`actions` service** beside `slots`. A row is a name, a description, an input schema, a risk (`read` / `write` / `destructive`, §39 §8 rule 1's tags) and an execute closure. `register` is non-transactional and returns a disposer, exactly like `SlotRegistry.register`, so a plugin registers inside `ctx.effect` and disposing the plugin removes the row. A plugin may register only the names its manifest's new **`actions`** key lists — the same gate §37 §5.3 already applies to `slots`, now on the callable surface.
- **One description, two consumers.** An action name is validated as 1–128 characters of `[A-Za-z0-9_.-]`, which is the intersection the WebMCP tool name rule and MCP's own require. §30's stdio server reads the same rows rather than restating them; that consumer is **not** wired here (D289 omits destructive tools outright, and D636 leaves it as a later task).
- **Enforcement reuses the primitives, it does not re-implement them.** A method-backed action *derives* its permission from `METHOD_PERMISSIONS` through the existing `decideCall`, so a generated tool cannot be more permissive than the button behind it; naming a different permission is refused at registration as drift. At call time `decideCall` decides again, so **both** halves a bridged call needs apply — the service is in the plugin's `inject` list *and* the permission is held — because checking only the permission would answer half of what the bridge answers. A local action names one of `PERMISSIONS`. Everything client-side can only **refuse** — OpenFGA and the credential broker remain the boundary (§37 §5.6's "client-side checks only shorten the path to a refusal").
- **Approvals are a seam with no default.** §39 §8 rule 1 makes `destructive` an `approve`, and `write` inside a *protected* environment an `approve`; rule 2 puts the gate in the credential broker and forbids the requester approving their own request. So a generated destructive tool with no gate wired resolves `approval_required` and `execute` never runs: **a destructive action is never auto-approved.** The two checks a client can honestly make are that a decision came back and that its decider is not the requester. Wiring the gate to the broker is a later task, and until then the refusal is the correct outcome rather than a gap.
- **The two fields the gate reads are required, not defaulted.** `risk` has no default: an absent one would be an un-gated action, which is a silent `allow` on the one declaration that decides whether a person is asked. And a `write` whose environment was **never resolved** to be unprotected is *gated*, because rule 1's default is "allow in non-protected environments" — a claim about a *named* environment, which a call that named none has not made. The environment a generated tool acts in is bound at generation by the host and is never a per-call parameter: an agent that could name its own would be naming its own `protected: false`, which is rule 2 again. For the same reason only the call's `signal` is read from the per-call options; an approval gate the agent supplies would be the requester approving its own request.
- **The approval proof is carried, not discarded.** Rule 2 says a destructive call *carries* the approval id and the broker verifies it against the call. So `execute` receives `context.approval` (`{ approvalId, decidedBy }`), because `execute` is the only thing that makes the call and the broker would otherwise have nothing to verify. It is absent when no gate was needed, so an `execute` must never present it unless it is present.
- **Refusals travel in the resolved value.** The draft reports a rejected `execute` as an opaque `UnknownError`, so every outcome resolves `{ok: true, value}` or `{ok: false, error: {code, message}}` with codes `unknown_action`, `permission_denied`, `approval_required`, `approval_denied`, `invalid_input`, `aborted`, `failed`. Nothing rejects; there is no caller that could do anything useful with an opaque error.
- **Annotations are derived, not described.** `readOnlyHint` follows the action's risk and `consequentialHint` is its inverse, so a harness filters on the annotation instead of parsing prose; `untrustedContentHint` is **always true**, because the input is an agent's and §39 §8 rule 5 says text from apps is never a basis for a tool choice on its own.

**What AP1d Task 4 established, by measurement on two Chrome channels (2026-10-05 and 2026-10-06)** (**D638**). Task 4 is the Chrome-flag CI job, and the measurement is what the job is built around: **the API's availability moves with the Chrome channel**, so the job asserts an invariant rather than one browser's answer.

- **The API's availability moves with the Chrome channel, so the job asserts an invariant rather than one browser's answer.** Measured under the same `--enable-features=WebMCPTesting,DevToolsWebMCPSupport`:

  | surface | Chrome 149.0.7827.155 | Chrome 154.0.8037.57 |
  |---|---|---|
  | `document.modelContext` | **absent** | **present** (a real `ModelContext`) |
  | `navigator.modelContext` | **present** | absent |
  | `navigator.modelContextTesting` | **present** | absent |

  On 149 the flag exposes the two `navigator` spellings and not the document attribute; on 154 the document attribute is there and the `navigator` spellings are gone. On 154 it is present **with no feature flags at all**, so it is no longer behind `WebMCPTesting` or an origin-trial token.
- **This corrects what Task 4 first recorded.** The original reading asserted the absent-API path and declared the real attribute unreachable token-free, on the strength of Chrome 149 alone. That was a single-channel conclusion drawn from the one browser the measurement happened to have; five channel versions later the attribute arrived, unflagged. The job now requires that the console **agree with whatever the browser reports**: absent → `not-exposed` and `register` resolving `undefined`; present → detection available, `register` returning a handle, `exposedTo` carrying only potentially-trustworthy origins, and sign-out unregistering **one abort per tool**. Both directions are asserted; neither is assumed. The first run of the job on Chrome 154 failed 8 of its 12 assertions precisely because it had pinned one channel's answer.
- **`navigator.modelContext` was a live decoy, and it is now gone.** On 149 it was a working registration surface under the flag — `registerTool`, `getTools`, `executeTool`, `ontoolchange` — so a plausible feature-detection written against it would have passed every jsdom test and found nothing in any real browser. No jsdom test can catch it, because `document.modelContext` is `[SecureContext]` and never exists there. The job asserts the decoys are never mistaken for the document attribute on **every** channel: on 149 the decoys are present and the API is not, on 154 the API is present and the decoys are not, and an identity check that the detected context **is** `document.modelContext` covers the rest.
- **The testing surface is `listTools()`, not `getTools()`.** On 149 `navigator.modelContextTesting` carried `listTools`, `executeTool`, `getCrossDocumentScriptToolResult` and `ontoolchange`. A vendor integration doc states `getTools()`; that is **wrong**, and it is corrected here rather than repeated.
- **What is primary, and what is not.** Primary: Chrome's own WebMCP page (read 2026-10-05, last updated 2026-10-01) naming the local switch `chrome://flags/#enable-webmcp-testing` and stating the origin trial runs **from Chrome 149**; and Chromium's own `third_party/blink/renderer/platform/runtime_enabled_features.json5`, where `WebMCPTesting` exists as `status: "experimental"` and appears in the `implied_by` list of the origin-trial feature `WebMCP`. **Not primary, and marked unverified in D638:** the `--enable-features=WebMCPTesting` spelling itself and the name `navigator.modelContextTesting` — both come from a vendor integration doc, and no primary page states them. `DevToolsWebMCPSupport` appears on **no** primary page and is measurably inert on 149: the surface set is identical with and without it. It is kept, because dropping it would weaken the job if a future Chrome needs it, and labelled rather than quietly deleted. **Note what the two-channel measurement does and does not settle:** it settles that the API's availability moves, and that the `navigator` spellings are gone by 154. It does **not** establish *why*, and no primary page was found that states the 154 gate.
- **The seam properties are asserted against a fixture on every build.** Only trustworthy origins reach `registerTool`, `clear()` is idempotent and unregisters one abort per tool, and a partial registration failure keeps the working tools — all run against a spec-shaped `ModelContext` installed on the **real** document, so the AbortSignals, the EventTarget and the promises are real. They are properties of `src/webmcp/index.ts`, not of any Chrome, and no browser reports its own `registerTool` arguments back, so a fixture is the only way to observe them. Where the build already has a native API the fixture shadows it **and records that it did**; the previous version refused to shadow one and so asserted nothing at all on exactly the build CI runs.
- **The job is deliberately tolerant.** Every assertion holds whether or not the flags still work — measured both ways, flags on and flags explicitly disabled, on both channels. A Chrome that renames or drops the features turns the job's *diagnostics* quiet, not the job red, and the browser's real answer (`typeof document.modelContext`, the `navigator` surfaces, the permissions policy, the resolved version) is printed on every run, so a channel change shows up in the log rather than only as a red build. The browser is resolved from the runner image and its exact version printed — channel-resolved, **not** version-pinned, which D638 says plainly. A missing browser **fails** the job on CI and skips it locally: a browser job that skips itself is green having tested nothing.
- **The API being reachable token-free does not make it load-bearing.** WebKit's position is `oppose`, so the absent path is still the production one and D568's enhancement posture is unchanged. What changed is only that the console can now be *tested* against a real `ModelContext` — which is a better test, not a stronger dependency.
- **No new dependency.** The harness is Chrome plus `Target.createTarget` and `Runtime.evaluate` over Node 22's built-in `WebSocket`, and `src/webmcp/index.ts` is transpiled from source on every run, so it cannot pass against a stale bundle. No Playwright, no Puppeteer, no browser binary in the lockfile — see `web/apps/console/browser/README.md`. (For contrast, §12's testing strategy names an AP1a "Playwright parity suite"; that suite is **not in the tree**, and this harness does not stand in for it.)

## 6. R2 Data Catalog and Iceberg interop (D571–D573)

Basin Catalog (formerly R2 Data Catalog; generally available since 2026-10-01) is a managed Apache Iceberg REST catalog inside an R2 bucket. Loams’ catalog is Lakekeeper (§08), which also speaks the Iceberg REST protocol, so interop is a catalog configuration, not a new format.

- **D571: `loams-iceberg` accepts an external REST catalog** (`catalog.kind = "iceberg-rest"` with URI, warehouse and a bearer token) beside Lakekeeper, using the Apache `iceberg-rust` REST client. **D572: read first.** Loams reads tables from R2 Data Catalog for DataFusion queries on day one; Cloudflare says external engines can write to it, but Loams **writes** only after a spike shows commits to that catalog pass the conformance tests (optimistic commit, snapshot expiry, compaction), and a table has exactly one writing catalog. **D573:** the provider is a vendor adapter and is open; the hosted analytics service built on Pipelines and Basin SQL is private (loams-platform doc 04). The catalog's REST endpoint, token scopes and prices were **not read (unverified)**; the spike confirms them.

## 9. Risks

1. Betas change or end; every adapter is optional and behind a trait. 2. Artifacts' billing date differs between two Cloudflare pages. 3. WebMCP may change again (it already moved from `navigator` to `document`). D638's measurement makes this concrete rather than theoretical, and it is a two-channel measurement: on Chrome 149 the local-development flag plants a working `navigator.modelContext` and a `navigator.modelContextTesting` while leaving `document.modelContext` absent, and on Chrome 154 the decoys are gone and the real `document.modelContext` is present with no flags at all — so the surface the console detects on moved, in both directions, inside five channel versions — hence feature detection, and hence a CI job whose assertions survive the flags being renamed. 4. A remote browser holds page content in a third party's cloud; D567 defaults to public-web work only. 5. The catalog's endpoint and token scopes may change with the Basin rename. 6. **A remote provider both bills and fetches.** A Cloudflare account is a prerequisite, and an agent that can navigate anywhere is an open proxy on someone else's card. The provider is off unless configured; it carries an egress policy (schemes, private and metadata addresses, deny and allow lists) enforced before every navigation **and** Browser Run session guardrails for what that check cannot see; guardrails are unavailable on Kitesurf, so an allow-listed Kitesurf session is refused; and concurrency, session spacing and a daily local budget bound the spend.
