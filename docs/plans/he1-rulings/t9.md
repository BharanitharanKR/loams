| R9.13 | **Plain views and `Distributed` tables** (Task 9, agent L). `CREATE [OR REPLACE] VIEW [IF NOT EXISTS]` is read by the House's reader and kept as a catalog entry of class `view` (an Iceberg table with no files whose properties hold the `SELECT`), so it is listed (`system.tables.engine = 'View'`), renamed, dropped (`DROP VIEW` or `DROP TABLE`) and undropped as a table is. The read path expands a view: its `SELECT` is held to the deny list as a read, the tables it names are resolved in the view's database and pinned like the statement's own (views over views to depth 8), and the worker makes `CREATE OR REPLACE VIEW d.v AS\n…` over their read views (invoker rights). `DESCRIBE` of a view is chDB's over that view. A view takes no rows (`INSERT`, `ALTER` and `OPTIMIZE` are `48`); a column list on `CREATE VIEW` is `48` for now. `ENGINE = Distributed(cluster, db, table[, …])` (also `AS t ENGINE = Distributed(…)`, `ON CLUSTER`) is §75 §7.3's topology syntax: a view of its local table that inserts write through to it, `FINAL` reaching the local table; `Distributed` leaves the deny list | Langfuse's `analytics_*` views; §75 §7.3; tests `catalog_views_and_distributed_tables` | Low: `system.columns` lists no columns for a plain view |
| R9.14 | **Readable `AggregatingMergeTree`, `Null`, and inner-table materialized views** (Task 9, agent L; D1570 scope). `AggregateFunction(f, T…)` columns are stored as ClickHouse's serialized state in an Iceberg `binary` field (written as `CAST(state AS String)`, read back by the views' `CAST(bytes, 'AggregateFunction(…)')`); `SimpleAggregateFunction(f, T)` columns as `T`. `ENGINE = AggregatingMergeTree` is a lake engine: reads without `FINAL` see the unmerged rows, so `-Merge` reads and plain aggregates over the state or simple columns answer as on ClickHouse; `FINAL` and compaction (`OPTIMIZE`, the scheduler) group by the sorting key with `fMergeState` for states, `f` for simple columns and `any` for the rest. `ENGINE = Null` reads no rows ever; its inserts are committed (the bucket keeps them) so its materialized views fire on them as on any source — Langfuse's `traces_null` → `traces_*_amt`. `CREATE MATERIALIZED VIEW mv [(cols)] ENGINE = … [PARTITION BY/ORDER BY/SETTINGS …] AS SELECT` (no `TO`) makes a lake table **named as the view** with the `SELECT`'s columns (as `CREATE TABLE … AS SELECT` reads them) and the view `TO` it, marked `inner`; `SELECT`, `INSERT`, `ALTER` (mutations included) and `DROP` of the name act on that table, and dropping the view drops the table. | R9.2 | **`VersionedCollapsingMergeTree` on lake tables (D1570)** is a fourth lake engine (`LakeEngine::VersionedCollapsing { sign, version }`; sign `Int8`, version an integer, `Date` or `DateTime` type; `Replicated…` accepted as D344). Without `FINAL` the rows read as written; `FINAL` (and `final = 1`) reads a merge view, and `OPTIMIZE` and the scheduler write what it reads. **The rule, measured on the 26.9.2.8 oracle**: per sorting key and version, rows in write order go through a stack, and a row of the other sign cancels the **most recent** row left, not the oldest (`+a +b −c` keeps `a`; `+a −b +c +d −e` keeps `c`). The view computes it with window functions over `(file sequence number, row number)`: keep rows whose sign is the group total's and whose `sign × running sum` is in `1 ..= |total|`, and of those the last per running sum. Pinned by `collapsing_final_matches_the_oracle` (the measured rows) and `collapsing_sessions_keep_their_latest_state` (OpenPanel's update pattern). With it, OpenPanel's replay (R9.3, `--strip`) matches the oracle on every `sessions` read; 97 of 105 distinct `SELECT`s match, 4 differ only in tied order, 4 wait for the inner-table views | Measured on the oracle, 2026-10-21 | Medium: a compaction writes a group's surviving rows sorted by the key, so a later cancel among more than one survivor of one key and version may pick another row than ClickHouse would (the House's write sort is not stable, which also affects `ReplacingMergeTree` ties within one `INSERT`) |
| R9.4 | **An `INSERT` into a lake table is written as ClickHouse writes an inserted block** (measured on the 26.9.2.8 oracle): sorted by the key and then by insert order (ClickHouse's writer sorts stably), and merged first as `optimize_on_insert` (on by default) merges it: `ReplacingMergeTree` keeps per key the greatest version, the last inserted among equals, and keeps `is_deleted` rows; `SummingMergeTree` sums per key, keeps the first row's other columns and drops all-zero keys; `VersionedCollapsingMergeTree` cancels as `FINAL` does (R9.2); `MergeTree` keeps every row. The House's write sort was not stable, so equal-version rows of one key in one `INSERT` (OpenPanel's `profiles` buffer flushes, Langfuse's ReplacingMergeTree tables) could resolve to another row than ClickHouse's, and reads without `FINAL` saw rows ClickHouse had already merged. The output `SELECT` numbers the staged rows with `rowNumberInAllBlocks()` under `max_threads = 1`. Pinned by `one_insert_merges_as_clickhouse_does`. `optimize_on_insert = 0` is not honoured (the House does not take the setting) | Measured on the oracle, 2026-10-22 | Low: a single-threaded read of the in-memory staging table per `INSERT` |

| R9.61 | **`DateTime64(7..9)` is a `long` of nanoseconds in a v2 lake table (D1572, owner 2026-10-22)**, amending D1551's interim rule. Measured first: SigNoz's DDL makes its trace and migration tables v3 (`timestamptz_ns`), and `loams-house-lake` refuses every v3 write ("Iceberg v3 needs row lineage"), so 10 of SigNoz's 28 tables with rows took none in the first replay. Now the column's Iceberg field is `long` when its type is `DateTime64(7..9[, tz])` alone, under `Nullable`, or as a `SimpleAggregateFunction`'s value; the table stays v2. The write path's output `SELECT` writes `toUnixTimestamp64Nano(c)` (a cast to an integer would give seconds); the read views read `fromUnixTimestamp64Nano(c[, tz])` and cast to the kept type, so the merge views (`FINAL`), compaction and `OPTIMIZE` go through the same conversion. A time transform of such a column (`toDate`, `toYYYYMMDD`, `toYYYYMM`, `toStartOfHour`) in `PARTITION BY` leaves the files unpartitioned by it, as R9.12 leaves any element without an Iceberg transform: Iceberg's time transforms take no `long`, and a truncation of a day in nanoseconds (8.64e13) does not fit `truncate`'s 32-bit width; the sort order stops at such an element. Inside an `Array`, `Map` or `Tuple` the type is still `timestamptz_ns` (v3, refused on write). Pinned by `nanosecond_times_match_the_oracle` (the 26.9.2.8 oracle's answers, before and after `OPTIMIZE … FINAL`: filters, `ORDER BY` on the key, `toDate`/`toStartOfHour`, `toUnixTimestamp64Nano`, zones `UTC`, `Asia/Kolkata` and none, a time before the epoch whose `toDate` is 1970-01-01, `ReplacingMergeTree` versions 1 ns apart, `SimpleAggregateFunction(min|max, DateTime64(9))`, an `ALTER … ADD COLUMN` with a nanosecond `DEFAULT`) and `views::tests::nanosecond_times_read_back_from_longs` | Owner, 2026-10-22; measured on the oracle | Medium: other engines read these columns as a `long` until v3, and a query on a nanosecond partition column prunes no files (the read view's conversion hides the column's statistics from chDB) |
