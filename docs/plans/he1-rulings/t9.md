| R9.2 | **`VersionedCollapsingMergeTree` on lake tables (D1570)** is a fourth lake engine (`LakeEngine::VersionedCollapsing { sign, version }`; sign `Int8`, version an integer, `Date` or `DateTime` type; `Replicated…` accepted as D344). Without `FINAL` the rows read as written; `FINAL` (and `final = 1`) reads a merge view, and `OPTIMIZE` and the scheduler write what it reads. **The rule, measured on the 26.9.2.8 oracle**: per sorting key and version, rows in write order go through a stack, and a row of the other sign cancels the **most recent** row left, not the oldest (`+a +b −c` keeps `a`; `+a −b +c +d −e` keeps `c`). The view computes it with window functions over `(file sequence number, row number)`: keep rows whose sign is the group total's and whose `sign × running sum` is in `1 ..= |total|`, and of those the last per running sum. Pinned by `collapsing_final_matches_the_oracle` (the measured rows) and `collapsing_sessions_keep_their_latest_state` (OpenPanel's update pattern). With it, OpenPanel's replay (R9.3, `--strip`) matches the oracle on every `sessions` read; 97 of 105 distinct `SELECT`s match, 4 differ only in tied order, 4 wait for the inner-table views | Measured on the oracle, 2026-10-21 | Medium: a compaction writes a group's surviving rows sorted by the key, so a later cancel among more than one survivor of one key and version may pick another row than ClickHouse would (the House's write sort is not stable, which also affects `ReplacingMergeTree` ties within one `INSERT`) |

| R9.61 | **`DateTime64(7..9)` is a `long` of nanoseconds in a v2 lake table (D1572, owner 2026-10-22)**, amending D1551's interim rule. Measured first: SigNoz's DDL makes its trace and migration tables v3 (`timestamptz_ns`), and `loams-house-lake` refuses every v3 write ("Iceberg v3 needs row lineage"), so 10 of SigNoz's 28 tables with rows took none in the first replay. Now the column's Iceberg field is `long` when its type is `DateTime64(7..9[, tz])` alone, under `Nullable`, or as a `SimpleAggregateFunction`'s value; the table stays v2. The write path's output `SELECT` writes `toUnixTimestamp64Nano(c)` (a cast to an integer would give seconds); the read views read `fromUnixTimestamp64Nano(c[, tz])` and cast to the kept type, so the merge views (`FINAL`), compaction and `OPTIMIZE` go through the same conversion.
