| R9.2 | **`VersionedCollapsingMergeTree` on lake tables (D1570)** is a fourth lake engine (`LakeEngine::VersionedCollapsing { sign, version }`; sign `Int8`, version an integer, `Date` or `DateTime` type; `Replicated…` accepted as D344). Without `FINAL` the rows read as written; `FINAL` (and `final = 1`) reads a merge view, and `OPTIMIZE` and the scheduler write what it reads. **The rule, measured on the 26.9.2.8 oracle**: per sorting key and version, rows in write order go through a stack, and a row of the other sign cancels the **most recent** row left, not the oldest (`+a +b −c` keeps `a`; `+a −b +c +d −e` keeps `c`). The view computes it with window functions over `(file sequence number, row number)`: keep rows whose sign is the group total's and whose `sign × running sum` is in `1 ..= |total|`, and of those the last per running sum. Pinned by `collapsing_final_matches_the_oracle` (the measured rows) and `collapsing_sessions_keep_their_latest_state` (OpenPanel's update pattern). With it, OpenPanel's replay (R9.3, `--strip`) matches the oracle on every `sessions` read; 97 of 105 distinct `SELECT`s match, 4 differ only in tied order, 4 wait for the inner-table views | Measured on the oracle, 2026-10-21 | Medium: a compaction writes a group's surviving rows sorted by the key, so a later cancel among more than one survivor of one key and version may pick another row than ClickHouse would (the House's write sort is not stable, which also affects `ReplacingMergeTree` ties within one `INSERT`) |
| R9.4 | **An `INSERT` into a lake table is written as ClickHouse writes an inserted block** (measured on the 26.9.2.8 oracle): sorted by the key and then by insert order (ClickHouse's writer sorts stably), and merged first as `optimize_on_insert` (on by default) merges it: `ReplacingMergeTree` keeps per key the greatest version, the last inserted among equals, and keeps `is_deleted` rows; `SummingMergeTree` sums per key, keeps the first row's other columns and drops all-zero keys; `VersionedCollapsingMergeTree` cancels as `FINAL` does (R9.2); `MergeTree` keeps every row. The House's write sort was not stable, so equal-version rows of one key in one `INSERT` (OpenPanel's `profiles` buffer flushes, Langfuse's ReplacingMergeTree tables) could resolve to another row than ClickHouse's, and reads without `FINAL` saw rows ClickHouse had already merged. The output `SELECT` numbers the staged rows with `rowNumberInAllBlocks()` under `max_threads = 1`. Pinned by `one_insert_merges_as_clickhouse_does`. `optimize_on_insert = 0` is not honoured (the House does not take the setting) | Measured on the oracle, 2026-10-22 | Low: a single-threaded read of the in-memory staging table per `INSERT` |
| R9.6 | **The gate is `openpanel_on_house_smoke`** (`scripts/house/app-on-house.sh openpanel`, CI job "House apps: OpenPanel on the House"): OpenPanel driven on the pinned oracle; a House built from the tree started on the runner (single node, TLS listener for the containers, which reach it as `house` through `host-gateway` and trust its certificate with `NODE_EXTRA_CA_CERTS`; OpenPanel's images stay unmodified, only their environment changes, `compose.house.yaml`); the oracle's traffic replayed against it (R9.3: the data now copied one oracle part per `INSERT`, and a read of a merging table without `FINAL` that differs is compared again with `final = 1` on both, `merge-timing`, never ignored); then the House emptied and OpenPanel itself run on it (migrations, ingest through its Redis buffers, the 58 page reads). It fails on any refused DDL, any differing `SELECT`, a failed migration, a lost event or a page error. About 2 minutes locally plus the build; it runs on the nightly dispatch and on pull requests touching the House or the harness, and stays out of `Connectors required` until OpenPanel passes (blocked on the inner-table `AggregatingMergeTree` views). The driver now waits for OpenPanel's last profile-buffer flush before reading | The owner's Task 9 exit: OpenPanel starts, ingests and renders on the House, checked against the oracle | Low |
