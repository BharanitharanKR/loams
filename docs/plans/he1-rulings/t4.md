| R4.1 | **OpenPanel 2.3.0's migrations fail on ClickHouse 26.7 and later.** Migration 14 creates an `AggregatingMergeTree` materialized view with columns outside its sorting key, refused by 26.9.2.8 unless the MergeTree setting `allow_dimensions_outside_sorting_key` is on (Umami hits the same check, R0.6). OpenPanel runs unmodified, so the oracle takes the setting from `apps/openpanel/he0-merge-tree.xml`; the House has to accept the same DDL | First `apps.sh openpanel up`, 2026-10-21 | Low |
| R4.2 | **The OpenPanel driver uses only its public HTTP surface** (Task 1's manifest entry checked: the stack comes up on the harness and `migrations = /app/packages/db/code-migrations` is the image's path; `up`, `drive` and `dump` take 69 s with images cached): tRPC `auth.signUpEmail` and `onboarding.project` (as the onboarding page does, which returns a write client and secret), `POST /api/track` with the secret (so the API's Redis buffers and the worker's batch inserts run), then 58 reads: every tRPC procedure the overview, report editor (line, bar, pie, metric, area, histogram, map, formula, funnel, conversion, sankey, retention), events, profiles, sessions and realtime pages call. It ingests a seeded week (`__timestamp`) plus a live pass, because OpenPanel opens sessions only for events newer than 15 minutes; it retries the first `/track` until the worker has written the day's salts (500 "No salt found" before), and sends `increment` only after the identified profiles are stored (404 before). Answers are kept raw under `.out/openpanel/responses/` (never committed) for Task 9's comparison | OpenPanel 2.3.0 API, read from the image (not committed, §75 §18) | Low |
| R4.3 | **OpenPanel's mined surface** (`conformance/clickhouse/inventory/openpanel.json`, 178 statements: 138 from the `query_log` of one drive on a fresh stack, 40 from the image's rendered `code-migrations/*.sql`; 106 sqlparser, 72 `EXPLAIN AST`, 0 unparsed; 164 features). **`windowFunnel` is used** (funnel and conversion pages); **`retention()` and `sequenceMatch` are not**: the retention page builds a matrix from `cohort_events_mv` with `groupUniqArrayIf` and `dateDiff`, so §75 §7.4 holds. Engines: `MergeTree`, `ReplacingMergeTree` (profiles, cohorts, groups, gsc), **`VersionedCollapsingMergeTree`** (`sessions`, written as sign −1/+1 pairs on every session update and read with `FINAL` or `sum(sign)`), and **6 `AggregatingMergeTree` materialized views with inner tables** (`CREATE MATERIALIZED VIEW … ENGINE = AggregatingMergeTree … AS SELECT`, no `TO`; `-State` combinators, read back with plain aggregates or `-Merge`). Syntax the House must take: `FINAL` (36), `WITH FILL` (38), `WITH ROLLUP` (8), `ANY JOIN`, `ARRAY JOIN`, scalar subqueries, `RENAME TABLE`, skip indexes (`bloom_filter`, `set`, `minmax`), TTL and `ALTER … MODIFY TTL`, `ALTER … ADD INDEX`, codecs, `ALIAS` columns, `enable_block_number_column`/`enable_block_offset_column` table settings. Mutations seen in its code (not yet in this run's traffic): `ALTER TABLE … DELETE WHERE` (imports, deletes), `DELETE FROM` (cohorts) and a lightweight `UPDATE` (profile backfill, `allow_experimental_lightweight_update`) | `loams-house-mine extract` at `dev` after #1003 (`4cbe4b8aa`, R2.8–R2.11), `--server` the pinned 26.9.2.8 | Medium: pages the driver does not open (imports, cohorts, groups, GSC) add features on a later run |
| R4.4 | **OpenPanel finding (upstream, not posted): on a fresh install four materialized views are attached to a renamed table.** Migration 3 creates `dau_mv`, `cohort_events_mv`, `distinct_event_names_mv` and `event_property_values_mv` on `events`; migration 8 then renames `events` to `events_20251123` and a new table to `events`. ClickHouse binds a view to its source by table identity, so the four views follow `events_20251123` and never receive another row: the retention page and the event-name and property-value pickers that read them are empty on a fresh 2.3.0 install on clickhouse-server too. **The House must bind a materialized view to its source table's identity, not its name, to answer as ClickHouse does** (Task 9 checks it). Not reported upstream without the owner's consent | `system.tables.dependencies_table` and `query_log` on the oracle | Low |
| R4.5 | **Asynchronous inserts are not in `query_log` as initial queries**: OpenPanel's buffers insert with `async_insert = 1, wait_for_async_insert = 0` (and `date_time_input_format = best_effort`, `parallel_view_processing = 1`), which 26.9 logs in `system.asynchronous_insert_log`, not as `query_log` rows of the client's query, so those settings are missing from the inventory. The harness now dumps `asynchronous_insert_log` too (`async_insert_log.tsv`, #1005: one row per buffer flush, for `events` and `profiles`), but it holds no settings, so they are recorded from the client code: `async_insert`, `wait_for_async_insert`, `date_time_input_format`, `parallel_view_processing`, `wait_end_of_query`, `mutations_sync`, `lightweight_deletes_sync`, `allow_experimental_lightweight_update`, `join_use_nulls` | `asynchronous_insert_log` on the oracle; OpenPanel's client code in the image | Medium |
| R4.6 | **OpenPanel re-mined with the settings proxy (R1.1)**: 181 statements, 0 unparsed, 167 features (3 more than R4.3: `setting:max_http_get_redirects`, `setting:date_time_input_format`, `setting:enable_http_compression`, which OpenPanel and clickhouse-js send at their default values).
